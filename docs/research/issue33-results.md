# Issue #33 multi-service interoperability: Windows observations, 2026-11-18

## Result and evidence boundary

All five final functional scenarios exited zero under the [prespecified method](issue33-method.md). The final records report ten unique encrypted files published, eleven expected positive recovery operations (including the observer's second recovery in D), and three expected failed decrypt attempts. A also recorded one rejected duplicate publication and one successful replay that is excluded from its unique recovery count. Every expected positive recovery authenticated and byte-matched. The five final JSON records report `scenario_completion_status: passed` and `failure_category: none`; expected rejections have explicit categories in worker CSVs. No unexpected scenario failure was observed in the final series.

This is a synthetic functional study on one Windows host. The source tree was dirty for all runs. These are working-tree observations, not fixed-revision release, capacity, availability, or security-strength results. The prior Issue #31 baseline remains a separate one-route characterization.

## Interpretation, risks, and future work

Observed observer recovery is the intended shared-trust behavior: an authenticated client with the envelope and key name can request data-key recovery under another recipient's key. It is not evidence of a bypass of per-key authorization, which CANIS does not implement. The certificate evidence establishes distinct test identities and TLS admission/rejection, not certificate-bound key restrictions or producer authenticity.

The A duplicate rejection and `.part` selection are harness behavior; the application has no native delivery deduplication or general directory watcher. C stops the server between operations using `Process.destroy()` and waits for it to exit; the event's `clean_exit` detail denotes that controlled lifecycle step, not a measured graceful-shutdown exit code. C does not exercise an interrupted write, a crash, an outage-duration objective, or durable recovery after host failure. The study uses only local loopback and temporary shared storage, with two small sizes already verified by CODE-03. It cannot establish scalability, availability, performance, security strength, large-file support, production readiness, or interoperability with non-Java clients. The server's wildcard bind and the local filesystem's atomic-rename and ACL requirements remain operational constraints. Future study work is a fixed-revision clean-checkout rerun, POSIX execution, and the separate Issue #34 fault series; none is claimed here.
