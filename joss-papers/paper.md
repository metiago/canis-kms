# Summary

CANIS-KMS is a Java key service and file client for asynchronous encrypted-file exchange through shared storage. [CODE-02 method](../docs/research/code02-method.md). The client encrypts a file locally and publishes a `CANISHYB1` envelope; a later authenticated client asks the TLS-protected service to recover the wrapped data key without sending the file contents through the service. [CODE-02](../docs/research/code02-results.md) exercised this workflow with separate processes. Under the documented shared-trust model, an admitted client can request recovery under any stored key name; the [JOSS-01 boundary test](../docs/research/joss01-results.md#focused-rerun-on-2026-11-17) observed that behavior. The completed studies characterize bounded synthetic correctness, resource use, delayed exchange, and selected faults, while the planned service-outage and local-control comparisons remain unmeasured. [Issue #31 baseline](../docs/research/issue31-baseline-results.md); [Issue #32 measurements](../docs/research/issue32-results.md); [Issue #33 scenarios](../docs/research/issue33-results.md); [Issue #34 scope](../docs/research/issue34-results.md).

# Statement of need

The authors describe sensitive file exchange among financial systems as the motivation for CANIS. [JOSS-01 historical record](../docs/research/joss01-results.md#historical-operational-evidence-and-research-motivation). That record describes a 2024 letter reporting production use of a predecessor KMS and records the authors' account of design continuity. The letter is not a repository publication artifact, does not name this code revision, and cannot establish deployment or compatibility of the current implementation. The completed CANIS evaluations use generated files and credentials rather than customer traffic; the size mix, arrival rate, and processing delays are study assumptions, not observations of the historical setting. [Issue #31 protocol and baseline](../docs/research/issue31-baseline-results.md#result-and-boundary).

The study asks what the shared-trust boundary permits and what the current Java file workflow does under a specified asynchronous load and selected faults. [JOSS-01](../docs/research/joss01-results.md#observed-evaluation), [Issue #31](../docs/research/issue31-baseline-results.md#result-and-boundary), and [Issue #34](../docs/research/issue34-results.md#result-and-scope) provide observed parts of that answer; no service-availability window was measured. The intended audience is software engineers, security engineers, and researchers examining file-based integration and trust boundaries. [JOSS-01 research-fit record](../docs/research/joss01-results.md#author-validated-question-audience-and-scope).

# State of the field

CANIS uses established AES-GCM and RSA-OAEP mechanisms rather than a new cryptographic primitive [@dworkin2007; @moriarty2016]; the repository's [JOSS-04 source review](../docs/research/joss04-results.md#primary-source-verification) records the standards behind these citations. That review also records that Google Tink documents KMS envelope encryption [@tink-envelope] and Vault Transit documents an envelope-encryption service [@vault-transit]. CANIS combines a Java file client, its own CANISP key-recovery service, and encrypted persistence under the documented shared-access policy. [CODE-02 method](../docs/research/code02-method.md#process-and-fixture-layout); [JOSS-01 comparison](../docs/research/joss01-results.md#comparison-grounded-in-primary-documentation). None of the completed experiments compares CANIS with Tink, Vault, or another KMS, so they establish no comparative security or performance advantage. [JOSS-01 scope](../docs/research/joss01-results.md#author-validated-question-audience-and-scope); [Issue #32 scope](../docs/research/issue32-results.md#result-and-scope).

# Software design

The Java 21 project has client and server Maven modules. [CODE-02 build method](../docs/research/code02-method.md#build-and-run). The client generates an AES-GCM file key, wraps it with a server-generated RSA public key, and writes a `CANISHYB1` envelope; the official decryption path returns only the unwrapped file key to the client. [CANISP and file-format guide](../docs/canisp-protocol.md#file-envelope-model); [CODE-03 implementation map](../docs/research/code03-results.md#implementation-memory-map). This keeps file bytes on the client/shared-storage path but gives an admitted client the recovered data key. [CODE-02 method](../docs/research/code02-method.md#process-and-fixture-layout); [JOSS-01 result](../docs/research/joss01-results.md#observed-evaluation). Whole-file reads and copies constrain the studied workload; [CODE-03](../docs/research/code03-results.md#supported-workload-boundary-and-streaming-decision) exercised files through 4 MiB on one Windows host, not a general maximum file size.

The server stores RSA key material in an AES-GCM-encrypted `CANISDB1` database and loads its database key from the external `CANIS_SECRET_KEY` file. [CODE-01 integrity record](../docs/code01-integrity.md#gap-analysis-and-implemented-plan). Local Windows checks found that invalid startup material and malformed stored records were rejected, and the [Issue #34 fault series](../docs/research/issue34-results.md#scenario-observations) found that damaged databases or mismatched master keys prevented restart until the matching synthetic backup was restored. The write sequence uses two moves rather than one transaction, and crash durability was not measured. [CODE-01 limits](../docs/code01-integrity.md#operational-and-compatibility-limits).

The official transport uses TLS 1.3: the server checks a trusted client certificate, the client validates the server certificate and hostname, and CANIS credentials follow the handshake. [CODE-02 method](../docs/research/code02-method.md#process-and-fixture-layout); [JOSS-02 verification](../docs/research/joss02-results.md#claim-and-limitation-assessment). Admitted clients share access to stored key names; the system does not impose per-service key authorization. [JOSS-01 boundary result](../docs/research/joss01-results.md#observed-evaluation); [Issue #33 scenario D](../docs/research/issue33-results.md#actual-scenario-observations). The research-only non-TLS loopback fixture used in Issue #32 is not a supported product transport. [Issue #32 method](../docs/research/issue32-method.md#prespecification-and-scope). CANIS does not verify audit-log integrity in this build: external hashes detected the Issue #34 test alterations, while CANIS continued the tested file workflow. [Issue #34 audit observation](../docs/research/issue34-results.md#scenario-observations).

# Research impact statement

The predefined [JOSS-01 synthetic boundary test](../docs/research/joss01-results.md#focused-rerun-on-2026-11-17) found that recipient and observer credential identities recovered the same file bytes, while an altered observer password was rejected. Its clients shared one certificate, so the result concerns credential-level shared access; observer recovery is consistent with policy, not a per-key authorization bypass. [JOSS-01 interpretation](../docs/research/joss01-results.md#observed-evaluation). A separate-process [CODE-02 smoke run](../docs/research/code02-results.md#ubuntu-ci-reproduction-on-2026-11-17) passed on a clean Ubuntu checkout; its local Windows negative cases rejected selected invalid inputs without recovered output. [CODE-02 outcomes](../docs/research/code02-results.md#commands-and-observed-outcomes).

The [CODE-03 Windows preflight](../docs/research/code03-results.md#raw-observations) verified two four-file attempts at each of 4 KiB, 256 KiB, 1 MiB, and 4 MiB, plus one 100-file schedule check. The absolute [Issue #31 CANIS baseline](../docs/research/issue31-baseline-results.md#result-and-boundary) byte-verified all 2,000 measured files in 20 scheduled 100-file runs. In the distinct fixed-revision [Issue #32 transport study](../docs/research/issue32-results.md#result-and-scope), the TLS path and a loopback-only research comparator each byte-verified 2,000 files over 20 paired runs. For the zero-delay, one-worker setting, the recorded median paired A-minus-B run-median end-to-end latency was +13.334 ms, with a five-pair range of −60.833 to +28.475 ms. [Issue #32 timing table](../docs/research/issue32-results.md#observed-latency-and-throughput). That difference includes admission and adapter effects and is not an isolated TLS cost. [Issue #32 limits](../docs/research/issue32-results.md#risks-and-limitations).

Five local [Issue #33 functional scenarios](../docs/research/issue33-results.md#actual-scenario-observations) demonstrated delayed recovery, distinct producer/recipient routes, recovery after a controlled restart with intact storage, admitted-observer recovery, and rejection of a changed authentication tag. In 21 isolated [Issue #34 storage/audit fault runs](../docs/research/issue34-results.md#scenario-observations), damaged database or master-key startup states were rejected and exact synthetic backup restoration allowed recovery; audit-line modification or deletion changed an external hash without a recorded application integrity rejection. These are tested outcomes, not availability or security-strength estimates. [Issue #34 limits](../docs/research/issue34-results.md#limits-and-operational-impact).

The measurements used one Windows loopback host and synthetic fixtures; Issue #31, #33, and #34 observations were made on dirty working trees, while the measured Issue #32 series used a clean fixed revision. [Issue #31 environment](../docs/research/issue31-baseline-results.md#environment-and-execution-record); [Issue #32 environment](../docs/research/issue32-results.md#fixed-source-environment-and-execution); [Issue #33 environment](../docs/research/issue33-results.md#environment-source-and-execution); [Issue #34 environment](../docs/research/issue34-results.md#environment-and-execution). The original local AES-GCM/local-envelope controls, scheduled service-outage windows, larger-file and distributed-storage workloads, and independent release reproduction remain future work. [Issue #31 protocol and deviations](../docs/research/issue31-baseline-results.md#reproduction-and-acceptance-review); [Issue #34 acceptance limits](../docs/research/issue34-results.md#reproducibility-and-acceptance-review). The completed studies support no general scalability, availability, production-readiness, cryptographic-strength, or external-adoption claim for this repository. [JOSS-01 limits](../docs/research/joss01-results.md#limitations-and-next-work); [Issue #32 limits](../docs/research/issue32-results.md#risks-and-limitations); [Issue #34 limits](../docs/research/issue34-results.md#limits-and-operational-impact).
